# KEYHOLE keys contract

One NFT contract: NEP-171 core, NEP-177 metadata, NEP-178 approvals, NEP-181 enumeration, NEP-199 payouts, NEP-330 source metadata. Each token is a viewing key; `tier` (1-3) sets access.

- `nft_mint(token_id, receiver_id, tier, metadata)`: minter only; deposit covers storage, excess refunded.
- One key per account: `nft_mint`, `nft_transfer`, `nft_transfer_call` and `nft_transfer_payout` refuse a receiver that already holds a key (`one key per account: receiver already holds a KEYHOLE key`). An account whose key is out on `nft_transfer_call` counts as a holder until `nft_resolve_transfer` runs (`pending_return_count`).
- `nft_approve` / `nft_revoke` / `nft_revoke_all` / `nft_is_approved`: NEP-178. Approvals are cleared on every transfer; `msg` triggers `nft_on_approve` on the approved account. A token holds at most `MAX_APPROVALS` (10) approvals (v2.3): an 11th `nft_approve` panics `approval cap reached: a token holds at most 10 approvals` before any state change or `nft_on_approve` call. Re-approving an account already on the list is allowed at the cap.
- `nft_payout` / `nft_transfer_payout`: NEP-199. 5% (`royalty_bps` 500, cap 10%) to the treasury, the rest to the seller; the payout always sums to the sale balance.
- `beat(token_ids)`: minter only; emits NEP-171 1.2.0 `nft_metadata_update`.
- `nft_set_tier(token_id, tier)`: minter only (v2.4). Raises a key's tier to `1..=3`, strictly above the current tier (a tier is never lowered); the token must exist. No deposit: the tiers entry already exists. Emits NEP-171 1.2.0 `nft_metadata_update` for the token. `holder_tier` and `nft_tier` read the new tier at once, and it survives `nft_transfer`.
- Key sale (v2.4, built in). The contract sells its own keys, so no third-party market is needed. Prices are in yoctoNEAR, from 0.1 NEAR (`MIN_LIST_PRICE`) to 100 000 NEAR (`MAX_LIST_PRICE`).
  - `nft_list(token_id, price)`, payable, owner only. A new listing attaches at least 0.01 NEAR (`LIST_STORAGE_DEPOSIT`). The contract keeps exactly 0.01 NEAR and refunds any excess at once. The seller changes the price with exactly 1 yoctoNEAR and the deposit stays. Emits `keyhole` 1.0.0 `key_list` `{token_id, seller, price}`.
  - `nft_unlist(token_id)`, 1 yoctoNEAR, by the seller or the current owner. The deposit goes back to the seller. Emits `key_unlist` `{token_id, seller}`.
  - `nft_buy(token_id)`, payable. The attachment must cover the price; the excess goes back to the buyer. The buyer may not be the seller and must not already hold a key (`one key per account`). The key moves through the shared transfer helper: approvals are cleared, exactly one NEP-171 `nft_transfer` is emitted with memo `sale`, and no `authorized_id` is named. The treasury receives `royalty_bps` of the price (rounded down, skipped at 0); the seller receives the price minus the royalty plus the listing deposit. Emits `key_sale` `{token_id, seller, buyer, price, royalty}`.
  - A stale listing (the key no longer belongs to the seller) cannot be produced by any public path, because every path ends the listing. If one is found anyway, `nft_buy` does not panic: it removes the listing, returns the deposit to the seller, refunds the attachment to the buyer and emits `key_listing_stale` `{token_id, seller, owner}`. The buyer gets a successful call with no sale, so a client must read the event.
  - Every other path that moves a key ends the listing and returns its deposit to the seller (with a `key_unlist` event): `nft_transfer`, `nft_transfer_call`, `nft_transfer_payout` (also through an approved marketplace) and `nft_resolve_transfer` when the key comes back to its sender.
  - Views: `nft_listing(token_id)` returns `{token_id, seller, price}` or null. `nft_listings(from_index, limit)` pages the listed keys in index order; `limit` defaults to and is capped at 100, and a start past the end returns an empty list.
  - Storage (no change to the `Contract` struct, so no migration from v2.3): listings are a `LookupMap` under prefix `L` (`Listing {seller, price, deposit}`). The index is kept by hand under `Mc` (count), `Ms` (slot to token id) and `Mq` (token id to slot). These prefixes do not collide with the `Key` variant bytes 0..=5, the approval keys `5` + `n`, the `pending/` markers or each other. An `UnorderedSet` cannot be used here, because its length lives in memory and a set built on demand always reads 0.
- Historical v2.5 (deployed, then superseded; the live contract is v2.7): handover admission + sealed pledge + treasury-only recovery.
  - E owner epochs, Vc pending counts and bounded Vo last-operation nonce; `begin_value_op` atomically binds current owner/epoch, prepaid positive storage growth and unique monotonic id before custody dispatch. Exact-id terminal-only finish; stale callbacks cannot unlock a later op.
  - Pledge migration is separate and one-time: pins attestor/custody contract/recovery beneficiary, starts lending OFF and preserves the v2.4 Contract layout. S/Q/A/F desk APIs are removed.
  - All title/listing/approval paths and value admission are locked while pledged or token transfer-call pending; reads/revocations remain available. Principal delivery, lender credit, default redirect, thaw and payout failures are nonce/phase-bound.
  - Immutable treasury-only recovery after December2,2026 02:00 Africa/Cairo preserves explicit liabilities, deposits, pending payout, storage and operating reserve. Legacy capital starts unattributed. Recovery cannot deploy code or change the owner. The v2.7 owner timelock below is a separate path and does not turn recovery into an upgrade. See [protocol interface](../../protocol/README.md) and [security authority graph](../../SECURITY.md#pledge-authority-graph--code-deployed-lending-off).
- `holder_tier(account_id)`: tier of the key the account holds (used by the TEE gate).
- `set_minter` / `set_royalty`: owner only, 1 yocto (`set_minter` disabled after pledge migration). `set_royalty(treasury, royalty_bps)` sets both the treasury and the rate. `nft_buy` reads them at buy time, so a change applies to open listings too.
- `migrate()`: v1 -> v2, self-call only, runs once. Turns on the approval maps; no token, owner, tier, metadata or config changes.

Build: `./build.sh` (omits optional embedded ABI; off-chain ABI JSON remains available) (rustc 1.86 via `rust-toolchain.toml`, cargo-near 0.22.0, near-sdk 5.17.2). The build is deterministic: CI rebuilds this source and compares it with the v2.7 line in `release/SHA256SUMS`, and checks that the committed v2.6 file is still `54ba51b3d7d256820e751c9fa4e0cda55c66b30111a186c6d9eff03b561b7b8a`. `./build.sh` refuses `--features sandbox-short-delay`. The wasm does not depend on the checkout path, but it does depend on the toolchain's sysroot: build with the rustup `minimal` profile (no `rust-src`), as CI does.

### Historical v2.5 notes (that candidate was deployed and is not the live v2.7 source)

That v2.5 build used certificate domain `KEYHOLE_SEALED_LOAN_V3_DELIVERY`. Funding creates backed borrower credit with `due_ns = 0`; debt starts only on the exact principal cashout's genuine successful native callback. A definite failed delivery restores credit and starts no debt; a lost callback stays UNKNOWN and locked, with no outcome signer. Provisional transfer-call title can be permissionlessly restored after 300 seconds if still unaccepted. Policy commands are single-flight: a lost action callback cannot be cleared by a Boolean view. These notes do not claim full missing-callback financial liveness. The live wasm is v2.7. Lending is off. See [protocol](../../protocol/README.md), [costs](../../docs/COSTS_AND_RISK.md) and [security](../../SECURITY.md).


### Prepaid payout account API (live on v2.7; these notes were first written for the v2.5 candidate)

`payout_storage_cost() -> U128`, `payout_account_registered(account_id) -> bool`, and payable `register_payout_account(account_id: Option<AccountId>) -> bool` implement one permanent prepaid payout slot per account. Attach the exact returned cost; omission registers the caller, and sponsorship is allowed. Current budget320 bytes covers the maximum account ledger/pending expansion and first pre-migration accounting metadata. Slots remain after success, so full seller/bond/buyer/approval/loan credits never fund their own storage by deduction. Duplicate/under/excess payments reject. Missing required registration reverts the operation, including an excess-price buy. These payout-slot rules are in the live v2.7 source. They supersede the v2.4 immediate-refund descriptions above. See [protocol](../../protocol/README.md#prepaid-native-payout-account-storage) for role onboarding and [SECURITY](../../SECURITY.md#round-four-payout-storage-budget-and-onboarding-historical-write-up-the-prepaid-slot-is-in-live-v27) for nonrefundable fees, old-candidate migration and unresolved callback-loss caveats.

### v2.7 (live)

Same Contract struct and Borsh layout as v2.6. No `new`, `migrate` or `migrate_pledge` call. Every new key sits under the raw prefix `Q27/` or the maps `Q27d` and `Q27o`. Release wasm `26d3deeff8a4445515d6356097bd7634e8b26deaee7e7ea1ebe47849b807c08c`, 519,382 bytes, from `./build.sh`. Unit proof: `cargo test --locked` (342 tests) and `cargo clippy --locked --all-targets -- -D warnings -A clippy::manual_range_contains`.

- Callbacks do not panic on state paths. A payout or treasury-recovery result is recorded before it is applied. If applying it fails, the pending marker and the record stay. `reconcile_payout(account_id)` and `reconcile_treasury()` (permissionless) apply only a recorded result, and never clear a marker whose result the callback did not record. A callback that never ran leaves its marker locked: the chain cannot recover that result. Predecessor checks: `payout_and_treasury_callbacks_reject_an_external_predecessor`.
- G1: `open_loan` reserves the deadline key inside the 0.009 NEAR bond (`loan_bond_covers_the_deadline_key_and_closing_frees_it`). `fund_loan` overwrites that key with a deadline 24 h later (`DISBURSEMENT_WINDOW_NS`). After it, the named lender may call `reclaim_unclaimed_principal(token_id, nonce)` (1 yoctoNEAR) if the borrower has not started the cashout. A deadline of 0, or a loan funded on v2.6 with no stored deadline, is refused. `claim_payout` and this call cannot both win: a dispatched cashout blocks the reclaim, and a reclaim leaves `claim_payout` only the remainder.
- Tier loan cap (L1): `open_loan` refuses a principal above the tier cap (Bronze 0.05, Silver 0.5, Gold 5 NEAR). `loan_cap(token_id)` reports it. Proof: `tier_caps_are_exact_per_tier_and_views_report_them`.
- Events (`keyhole` 1.0.0): `loan_fund`, `loan_repay`, `loan_cancel`, `loan_default`, `loan_reclaim`, `payout_claim`, `collateral_ready`, `lending_toggle`, `treasury_recover`, plus `loan_principal_delivered` (existing) and the governance events below. Proof: `loan_lifecycle_emits_the_named_events` and `cancel_and_default_events_are_emitted`.
- Governance has no single-step `set_owner`. `propose_owner` names a successor and starts the same 24 h delay as an upgrade (`MIN_UPGRADE_DELAY_NS`). The current owner stays in control and may `cancel_owner_proposal`. Only the named account can `accept_owner`, and only after the delay, which proves that account can attach 1 yoctoNEAR. The contract account is refused as a successor. Accepting clears a staged upgrade, so a parallel handover applies the staged wasm first. Repeating a proposal overwrites the same key and restarts the delay. Proof: `owner_handover_is_two_step_and_only_the_proposed_account_accepts`, `a_bad_owner_proposal_can_be_cancelled_before_it_can_take_effect`, `accepting_ownership_clears_a_staged_upgrade`, `propose_owner_and_accept_owner_reject_the_contract_account`, `parallel_owner_and_upgrade_timers_apply_before_accept`.
- `stage_upgrade(code_sha256)` stores one lowercase sha256. `cancel_upgrade` drops it. `apply_upgrade` is owner only, after the delay, and the wasm is the raw input. A hash mismatch or bytes that do not start with the wasm magic do not consume the stage. A matched module is deployed with no migrate call, and that apply consumes the stage. Proof: `upgrade_stage_cancel_timelock_and_hash_checks`. The release constant `RELEASE_UPGRADE_DELAY_NS` is 24 h. `./build.sh` refuses the `sandbox-short-delay` feature and sets `cfg keyhole_release`, which does not compile together with that feature. Proof: `release_delay_is_24h_and_the_release_script_refuses_the_sandbox_feature`. The sandbox fixture is `contracts/keys/build-sandbox-delay.sh` and is not a release artifact.
- After the write, the same receipt refuses a governance change that would spend legacy listing bonds, user liabilities, treasury, a pending recovery, or the operating reserve. The listing, liability, pending and operating terms are shared with treasury recovery. Proof: `judge_governance_budget_omits_legacy_listing_reserve`, `judge_wind_down_storage_budget_underestimates_actual_write`, `governance_storage_cannot_consume_user_liabilities`.
- `wind_down` closes new activity on or after 2027-02-01T00:00:00Z (`WIND_DOWN_NS`, not shortened by the sandbox feature): `nft_mint`, `nft_list`, `open_sale`, `open_loan`, `register_collateral`, `fund_loan` and `buy_sale` refuse once it has run. It is refused while user liabilities are above zero, while a treasury recovery is pending, or while a key is listed. It is not a pause: transfers, repayments, claims and payouts keep working. Proof: `wind_down_refuses_before_date_then_closes_new_activity_and_keeps_transfers` and `wound_down_refuses_funding_and_a_protected_purchase`.
- `version` and `valid_until` on `register_collateral` stay `u64`. The worker sends JSON numbers (`tee/worker/src/collateral.rs`). `expected_owner_epoch` stays a JSON string. `beat`, `nft_set_tier` and `finish_value_op` stay deposit 0 so a FunctionCall key can call them. The beat key is that FunctionCall key. The minter account also has a full-access enclave key for payable `nft_mint`, `register_collateral` and `begin_value_op`.
