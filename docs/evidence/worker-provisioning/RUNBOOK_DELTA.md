## Native send reconcile: public RPC shapes observed 2026-11-12 (read-only)

Checked on rpc.mainnet.near.org and free.rpc.fastnear.com (both identical). `EXPERIMENTAL_tx_status` with wait_until NONE for an unknown hash returns immediately a JSON-RPC error: `{"jsonrpc":"2.0","error":{"name":"HANDLER_ERROR","cause":{"info":{"requested_transaction_hash":"<hash>"},"name":"UNKNOWN_TRANSACTION"},"code":-32000,"message":"Server error","data":"Transaction <hash> doesn't exist"},"id":"dontcare"}`. The same call with wait_until FINAL returned nothing within 30 s, which is why the worker asks with NONE first. `EXPERIMENTAL_protocol_config` (finality final) returns `result.transaction_validity_period = 86400` and `result.epoch_length = 43200`. `block` by height or hash returns `result.header.height`; a block already garbage-collected returns `{"name":"HANDLER_ERROR","cause":{"info":{},"name":"UNKNOWN_BLOCK"},"code":-32000,"message":"Server error","data":"DB Not Found Error: BLOCK: <hash> \n Cause: Unknown"}`.

Liveness and operations. New sends store the reference block height and hash in the plan at signing time (reference_height; journals written earlier lack the field and still load), and a send is refused before signing if the final block response has no parseable height. A stored height needs no block lookup at clear time. A legacy ticket (no stored height) uses only the original rule: the host must be able to retrieve the reference block (to learn its height), final height must be >= reference height + 86400 + 2, the signer key's final nonce must be below the plan nonce, and the status must be the structured UNKNOWN_TRANSACTION. There is deliberately NO inference from an unknown or missing reference block: a lagging, state-synced or load-balanced RPC can report UNKNOWN_BLOCK for a fresh block, so an unretrievable reference block means the claim is kept.

Retention basis (nearcore client_config.rs): MIN_GC_NUM_EPOCHS_TO_KEEP = 3 and DEFAULT_GC_NUM_EPOCHS_TO_KEEP = 5, and GCConfig::gc_num_epochs_to_keep() returns max(MIN, configured). With the minimum of 3 epochs of 43,200 blocks a node keeps at least 129,600 blocks, which exceeds the 86,400-block validity period; the 107,922 blocks observed on the public nodes sit between those bounds because GC is epoch-granular. So a reference block stays retrievable for at least about 3.4 hours (about 21,600 to 43,000 blocks) after it expires. The validity rule in nearcore (check_transaction_validity_period) also treats a transaction whose base block header cannot be loaded as Expired and requires the base block to be an ancestor of the head. Operational rule: run reconcile_minter_send repeatedly, starting at the earliest possible expiry (final height >= reference height + 86402), until it clears or finishes the send; do not wait. If the reference block is garbage-collected before a clear, the claim is NOT cleared automatically: that needs a manual reviewed recovery.

## Holder withdraw without confinement, and pending rows that settle (2026-11-12)

Withdraw. The only holder withdrawal is the exact USDC exit to a NEAR account, which is the three hops OutLayer gave devmo: POST /wallet/v1/confidential/unshield, POST /wallet/v1/storage-deposit with account_id = the recipient, then POST /wallet/v1/intents/withdraw with chain near and async true (OpenAPI 0.1.0-alpha.4 schemas ConfidentialUnshieldRequest = {token, amount}, StorageDepositRequest = {token, account_id}, WithdrawRequest = {chain, to, amount, token, async}; for chain near the WithdrawRequest description says a nep141:<token> value delivers that NEP-141 to a storage-registered recipient, so nep141:<USDC> is accepted). Each hop is journaled, uses its own idempotency key, and is read back at FINAL before the next; a reconcile resumes at the next hop and never repeats a hop that is confirmed. The previous gate required a reviewed confinement proof (confinement_v1) even for a plain holder vault and failed with "final commit marker missing". Now exact_exit_policy requires that proof only for a vault that has one, or that carries collateral: with no marker, no pledge, no loan and no collateral binding the standard holder exit runs (the worker sends only to the holder using the vault's own wallet, and the proof is skipped because there is no lien to protect; all other guards unchanged: fresh full-access NEP-413, recipient equals the current holder, caps and spend reservation, cooldown and lock checks, no listing, owner epoch, value-op begin/finish on chain, journal and recovery pointer). A vault with a loan, pledge or collateral binding but no confinement is refused with code exit_not_enrolled. Provider row types per hop: unshield confidential or confidential_unshield (the latter is inferred from the live confidential_swap, NOT yet observed), storage call, withdraw withdraw; a refusal names step, id_match, type and error_present.

## Wall-clock budget, resumable exit hops and spend holds (2026-11-12, worker ed0f614a withdraw timeout)

Live finding: the first real withdraw (call ac75d5aa-f91a-4737-b5de-e1bb4a8ab546, 20:06:12 UTC) was killed by OutLayer with "WASM execution timed out after 60 seconds (penalty)" (21,631,890 instructions, time_ms 71826). No begin_value_op or other minter transaction landed, the pending count stayed 0 and balances did not move, but spent_today rose by 10000 micro-USD. Cause (from the code; the enclave gives no per-stage timing): one call chained every phase synchronously: authenticate and guard_preflight (about ten chain views, repeated inside guard_begin), the exact-exit policy views, the spend reservation, the native begin_value_op send (a FINAL wait), and then all three exit hops inline in exact_exit::drive, each hop doing validate_dispatch, a FINAL readback observation (two provider GETs and five chain views), the POST, a re-read and a second observation. That is far more than 60 s of host round trips; only the swap (one POST) fit. The call limit is OutLayer's default 60 s (https-api docs: resource_limits.max_execution_seconds default 60, maximum 180; neither the CLI nor the web gateway sent it, and the gateway aborts at 55 s).

Fix. A per-call wall-clock budget (budget::TOTAL_MS = 50 s, started in authenticate) gates every phase: the spend hold is made only if the call is at most 20 s old; guard_begin refuses (time_budget) unless 25 s remain for the FINAL begin send; and exact_exit::drive starts a hop only with 22 s left, otherwise it returns status processing with step, value_op_id and reason time_budget. The next call, a holder-signed reconcile_value_op of the original id (the CLI prints the id), resumes exactly there: a verified hop is skipped, a posted hop is polled and never posted again, so the three hops complete over several short calls with one POST each. One case is NOT auto-resumable: if the call is killed after a hop POST but before the provider id is stored, the next drive sees the dispatch claim with no id and returns status needs_review (exact_exit.rs: "Never retransmit after lost response, even under the original key") — re-posting could double-send, so that case needs a human review, not another reconcile. The CLI now sends resource_limits.max_execution_seconds = 120 for swap, quote, withdraw and reconcile; the web gateway (web/app/api/worker/route.ts) still needs the same resource_limits and a longer abort than 55 s, and the UI should show "Sent, confirming" for status processing and reconcile automatically (each reconcile needs a fresh wallet signature, not a session).

Spend holds. guard_begin now gives the hold back, and marks the journal abandoned (confirm_admission refuses an abandoned journal, so it can never be begun later without a hold), whenever no begin_value_op could have been sent: any failure before the journal exists, a failed journal write or pointer write, the time gate, and a begin refused with native_busy, guard_state, rpc, collateral_unknown, time_budget, legacy_versions, value_op_pending or not_owner. native_unknown and admission_unknown keep the hold, because a send may have landed. A call killed by the platform after charging cannot release; the 20 s gate keeps that window small. The 10000 micro-USD already counted for call ac75d5aa cannot be corrected by the holder or this change: the counter is enclave storage keyed by token and UTC day and the worker has no admin op to decrement it; it resets with the UTC day (daily cap 5,000,000, used 64,100), so the practical impact is nil.
